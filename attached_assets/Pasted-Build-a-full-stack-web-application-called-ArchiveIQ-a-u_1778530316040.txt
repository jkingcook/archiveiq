Build a full-stack web application called "ArchiveIQ" — a universal 
archival super intelligence platform. Node.js + Express backend, 
vanilla HTML/CSS/JS frontend, single index.html. Fully deployable 
on Replit.

===================================================
## CORE PHILOSOPHY — SHARED INTELLIGENCE
===================================================
ArchiveIQ is not a scanning tool. It is a living intelligence platform 
where every component shares a common memory and communicates with every 
other component in real time.

The Shared Intelligence Bus is a global server-side state object that 
ALL modules read from and write to:

const INTELLIGENCE_BUS = {
  projects: {},           // all projects and their configs
  activeProject: null,    // currently active project
  itemStore: [],          // all processed items across session
  analysisStore: [],      // all analysis results
  patternLibrary: {},     // patterns learned across all items
  crossProjectIndex: {},  // people/places/themes across ALL projects
  sessionLog: [],         // full activity log with timestamps
  schemaRegistry: {},     // all saved schemas by project
  protocolRegistry: {},   // all saved protocols by project
  exportQueue: []         // pending exports
}

Every API route reads from and writes to INTELLIGENCE_BUS. No module 
operates in isolation. When a new item is processed, the pattern library 
updates. When analysis runs, it reads from all items across the project. 
When exports generate, they pull from the full intelligence state.

### Built-in Machen Protocol
When Machen Family Papers project is active, pre-fill protocol with:

"""
MACHEN FAMILY PAPERS — DIARY PROCESSING PROTOCOL V.3
Compiled by Lyndon W. Cook, Hendersonville, Tennessee, May 2026.

SOURCE DESIGNATION: The Minnie Gresham Machen daily diary is a HEADLINE 
SOURCE. Voice-category extractions preserve direct quotation of Minnie's 
actual prose with sufficient context to be comprehensible without the source.

SOURCE HIERARCHY:
- Level 2 (Canonical): Typescript transcription. THE CANONICAL SOURCE.
- Level 3 (Working): OCR-scanned digital version. One degree removed.
  Subject to OCR errors the typescript does not contain.
- Master Transcript: Project owner's clean corrected version.
- No holograph diary volumes extant. Verification = OCR-correction-
  against-master-transcript, NOT holograph-verification.

THREE-PASS WORKFLOW:

PASS 1 — COVERAGE VERIFICATION:
Day-by-day verification the typescript covers the calendar year. Track 
across upload batches. Identify: missing days, duplicate-with-mis-dating 
sections, missing date headers, brief entries. Day-of-week verification 
is the standard tool for date-header ambiguity. Produce coverage report 
by month with cumulative-coverage statement.

PASS 2 — OCR / ANOMALIES CATALOG:
Category 1 — Probable OCR errors (rn/m, cl/d, ff/pf confusion, broken 
  words at line breaks). Known corrections: Posher's→Posner's; 
  Beney. Soc.→Benev. Soc.; Hambelton→Hambleton; Mt. Roland→Mt. Royal; 
  Brook Bird→Brooke Bird; Von Kappf→Von Kapff
Category 2 — Multi-word confusion. Roland/Rowland/Royal triple confusion 
  is a documented recurring Baltimore-area pattern — flag all three when 
  any appears. Verify all three.
Category 3 — Name and term ambiguities. Flag for verification.
Category 4 — Substantive lacunae. Shorthand passages → preserve as 
  Provenance rows. Pattern: Minnie used shorthand for private content.
Category 5 — Coverage gaps (cross-reference Pass 1)
Category 6 — Period usages preserved as authentic (do NOT modernize):
  "Telegram" (Rowland Multiplex device), "type-written" (period 
  hyphenation), "Indian Ter." (1902 abbrev), "Aunty" (family naming), 
  "wheel-ride" (period bicycle usage)
Category 7 — Substantive content flags for Register attention

STANDARDIZATION vs PRESERVATION:
STANDARDIZE: OCR introduced corruption the typescript itself does not 
  contain.
PRESERVE: Typescript reads the word as Minnie actually wrote it.
Ambiguous cases → flagged for project-owner resolution.

PASS 3 — REGISTER EXTRACTION:
Build Register row blocks at day-and-event level. One entry = 0–8 rows 
depending on content density. Apply donee-locator priority to shape 
extraction granularity. Voice rows = direct quotation, never paraphrase.

DONEE-LOCATOR PRIORITY:
Category A (Highest — LOC mss86777): Minnie's own voice, Loy Gresham 
  references (every mention), Generation II Gresham-side family network, 
  Arthur Sr. daily life and legal practice
Category B (High — Westminster): J. Gresham Machen biographical material 
  (every activity, decision, illness, social engagement), ecclesiastical 
  and theological trajectory, 1925–1928 Princeton Seminary controversies
Category C (High — Princeton/Wilson): Wilson dinner attendance, October 
  1902 Princeton presidential inauguration, Wilson and Patton references, 
  1894 Wilson holograph acceptance letter context
Category D (Standard): General biographical material
Category E (Specialized): Hopkins University Special Collections; 
  Mrs. Rowland connection; Confederate Bazaar Georgia Table; 
  Phinizy/Augusta GA connection; Mrs. Burton late-life 1925–1928

DONEE SEQUENCING PRIORITY:
Tier 1: 1899-1901; 1928-1925 (reverse); 1913
Tier 2: 1894-1898; 1914-1916; 1917-1924
Tier 3: 1890-1893; 1903-1912
Prototype: 1902

CITATION CONVENTIONS:
Standard: "Minnie diary [year], [date] entry"
Multi-day: "Minnie diary [year], [date] entry ([event anchor])"
Donee-anchored: "[citation] (strengthens [Westminster/Princeton-Wilson/
  Hopkins/LOC] case)"
First-order: "Anderson, The Sharples-Sharpless Family, entry 9024"
Second-order: "[source] (via Suppl. A § 1)" or "(via Master Doc v.2)"
Project synthesis: cite "Project synthesis."

VERSIONING BY ADDITION: Entries never deleted — superseded by clarifying 
entries with explicit cross-reference.

PHASE A SKIP: Do NOT do Master-Document-narrative back-extraction before 
the typescript. Work is deferred to a single proper pass at first-order 
primary source.
"""

  Project: [project name]
  Project type: [type]

  [FULL SAVED PROTOCOL]

## SHARED INTELLIGENCE BUS — DETAILED SPEC
===================================================

All routes import and mutate a single module-level state object:

const INTELLIGENCE_BUS = {
  projects: {},
  activeProject: null,
  itemStore: [],
  analysisStore: [],
  patternLibrary: {
    people: {},      // name → {count, projects, dates, items[]}
    places: {},      // place → {count, projects, items[]}
    themes: {},      // theme → {count, projects, items[]}
    dates: {},       // year → {count, items[]}
    categories: {}   // category → {count, items[]}
  },
  crossProjectIndex: {
    sharedPeople: {},
    sharedPlaces: {},
    dateOverlaps: {},
    thematicOverlaps: {}
  },
  sessionLog: [],
  schemaRegistry: {},
  protocolRegistry: {},
  exportQueue: []
};

After EVERY item is processed:
1. Push item to itemStore
2. For each person in people_extracted: update patternLibrary.people
3. For each place in places_extracted: update patternLibrary.places
4. For each date in dates_extracted: update patternLibrary.dates
5. For each keyword/theme: update patternLibrary.themes
6. For each category in register_rows: update patternLibrary.categories
7. Update crossProjectIndex with cross-project intersections
8. Append to sessionLog: {timestamp, action, item_id, project_id}

full data) for the live status bar.

===================================================
## ERROR HANDLING
===================================================
- Malformed JSON from Claude: retry once, save raw, flag needs_review
- Unreadable image: skip, log, continue batch
- API rate limit: auto-pause 5s, resume
- Missing API key: setup modal on load with instructions
- PDF conversion failure: skip, log, continue
- Bus update failure: log error, do not halt processing
- Always continue batch — never halt on single item error
